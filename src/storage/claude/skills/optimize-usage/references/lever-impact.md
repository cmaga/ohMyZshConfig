# Lever impact

One number per lever, 0-100: how much degrading this lever degrades the final deliverable. Session model = 100 is the anchor — never step it lightly.

| Lever | Impact | Why |
|---|---|---|
| Session model | 100 | Defines the entire solution space — plan, scope, tests, review standards. Every downstream token executes its decisions, so its errors compound through the whole ticket. Nothing gates it. Published evals (2026-07): Opus 5 matches or beats Fable 5 on coding (SWE-bench Verified 96.0 vs 95.0, SWE-bench Pro 79.2 vs 80.3) at half price — the fable→opus step is evidence-flat for coding work; the 100 covers the full span down to haiku. |
| Review model | 60 | The last gate; its misses ship. Strong review is also what makes cheap workers safe — degrading it weakens every other lever's safety argument. |
| Session effort | 50 | Same blast radius as session model, but shallower per step: published data shows max/xhigh/high nearly equivalent — on Opus 5, max often scores at or below xhigh (Frontier-Bench 43.3 vs 44.4) — so steps here move quality less than model swaps. |
| Review effort | 35 | Thoroughness is the whole job of review; lower effort trims exactly the double-checking the role exists for. |
| Worker model | 25 | Fallback for cards that name no model. Executes fully specified task cards inside a solved problem, and every diff passes two gates. A month on sonnet showed no recorded quality drop. |
| Mechanical worker model | 10 | Cards whose work a committed integration test verifies. The test is ground truth, not supervision — the worker iterates until green or trips a stop rule, so a weak model costs iterations rather than correctness. The cheapest lever in the pipeline to step, and the reason haiku is viable at all. |
| Judgment worker model | 30 | Cards where the right answer is not fully written down and the model has to notice something unstated. This is exactly where a model that does precisely what it was told and nothing more fails, and no test catches it — the test only encodes what someone already thought of. Step this last among worker levers. |
| Worker effort | 10 | Left at `inherit` deliberately — workers track session effort. Cards are scoped, and quality risk is bounded by the committed tests a worker iterates against rather than by a downstream gate. |
| Research fan-out model | 8 | Deep-research fan-out (dev-workflow Step 4.1): read-and-summarize online research every tier is saturated on. Output is intermediate and the parent session model synthesizes it, so a cheap model here is near-free — the safest fan-out to cheapen first. |
| Code fan-out model | 20 | Codebase-fit fan-out (dev-workflow Step 4.2): analyzes real code to claim placement and reuse that shape the plan. A wrong reuse claim is the classic failure that step exists to catch; adversarial verification gates it, but degrade more cautiously than research fan-out. |
| Review fan-out model | 45 | The finder subagents are where detection actually happens. A bug a finder misses is caught by nothing downstream — unlike a bad finding, which the disproof step filters — so this lever is asymmetric: cheapening it loses bugs silently. Below review model (60) only because the parent still frames the review, splits the units, and makes the final call. |
| Review fan-out effort | 25 | Same agents, shallower per step — the model-to-effort ratio the other paired levers show. Split personality: the disproof half gets one claim and is told to refute it, which is the most effort-insensitive work in the pipeline; open-ended finding is not. Rated for the finders. |
| Tester model | 50 | Writes the failing integration tests every worker is judged against, before any code exists. Asymmetric like review fan-out (45), and rated above it: a thin or shallow suite does not produce a bad result, it produces no result — the workers simply have less to satisfy, and nothing downstream notices. Cheapening this silently weakens the safety argument for every worker lever, so never step it to fund a worker step. |
| Vault-scribe model | 15 (est.) | Writes knowledge-vault notes. Output is gated — the user approves a content summary before it lands — so errors are catchable, but notes are durable context for future sessions and quality drift compounds quietly. Unbenchmarked estimate (2026-07-21). |
