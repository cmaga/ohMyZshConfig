# Fire

Production is broken and users are being hurt now. Work the incident with the user, from the symptom they describe to the harm stopped and its follow-ups filed. Stopping the harm fast comes first; the long-term fix goes through the normal pipeline afterwards, as its own ticket.

Fire runs only with the user here. Each numbered step ends in its report and waits for the user's "go" before the next one starts. An answer to the report's question finishes that step; any other reply changes the next one; only go starts it. Reads within a step need no go.

Read production and never drive it: no test transactions, writes, restarts, or config changes beyond what the plan the user said go to names. Never put a secret in chat, a ticket, or a file; a step that needs one is the user's to run.

SKILL.md's Non-negotiables and recipes give way to this file: no task list, order, intake, contract, tasters, or verdict before a merge, which the follow-up tickets get. A defect in this skill found mid-incident becomes a skill lesson once the harm has stopped, never a stop.

Keep each report to a few lines per [Writing the reply](../../SKILL.md#writing-the-reply): the finding first, every claim with its evidence or labeled measured, inferred, or guess, and at most one question, last. Note the time of each event as it happens (`date`): harm began, cause found, mitigation shipped, harm stopped, for the hand-off.

The `## Production` section of the project rules (`.claude/kitchen/house.md`) names where errors, logs, and data live, how a deploy rolls back, and whether the default branch takes direct pushes. When it is missing or lacks a line, ask for what it lacks in one question before step 1, and take "don't know" as an answer; their answer starts step 1. Whenever the session ends, add what the user told you to that section in their checkout, creating it from [the template](../open/templates/house.md) when missing, uncommitted, for them to commit.

1. **Root cause.** Find what broke and what set it off. Pin down when it began from the first bad signal: the error tracker's first-seen ([Sentry](../cook/stations/why/sources/sentry.md), [Datadog](../cook/stations/why/sources/datadog.md)), the logs, the data, or the user's report. Then list every change shortly before it: merges and deploys (`git fetch`, then `git --no-pager log --since=<a day before it began> origin/<default branch>`), config and infrastructure changes (the platform's release or audit log), dependency bumps, and the status pages of outside services. Never assume the latest deploy is the cause; confirm the suspect touches the failing path. Read that path yourself, and use the [how](../cook/stations/how.md) station only when it spans more than a few files. Report the mechanism, the change or outside cause behind it with its link and time, and how sure you are.
2. **Impact and severity.** Who is hurt and how: which users and flows, how many so far and at what rate, since when, and whether it still happens or will recur (a scheduled job's next run). Count from the error tracker, logs, analytics, or read-only queries on production data, each number with the query behind it. A number no source holds is reported unknown, with what would count it. Name what is at stake beyond the error: money taken or owed, data lost, wrong, or exposed, a secret exposed, users locked out. Then rate the severity from it. The higher it is, the more a mitigation may cost users to stop it.
   - SEV-1: a core flow broken for most users, money taken wrongly, data lost, corrupted, or exposed, or a security breach.
   - SEV-2: real harm or lost revenue for some users, with no workaround.
   - SEV-3: limited harm with a workaround.
   - SEV-4: cosmetic or an edge case. It is not a fire: offer to file it through the `ticket-provider` skill, file it on a yes, and end with a short reply.
3. **Mitigation options.** List every way to stop the harm that the root cause allows: revert the change, roll back the deploy, restore a config value, turn a feature flag off, rotate or revoke a credential, repair the data, hotfix forward, disable or degrade the feature, throttle, fail over, maintenance mode, or wait. For each, say what it stops, what users lose, how long it takes, how it is undone, and the check that will show it worked. Leave out an option that cannot work, with why in one line. What users lose:
   - A rollback takes out every change since the target release, its config included, and the bad change stays on the default branch until it is reverted. Check whether it undoes the change's data writes and migrations.
   - A revert takes out what else uses the reverted code.
   - A flag or config value reaches everyone it covers, not only the users being hurt.
4. **Plan.** Recommend the option that leaves the fewest users harmed for the least time, weighed against what it costs them at this severity, and say why it beats the next best. Write it as the exact commands in order, each with its check and its undo, marking each step only the user can run. A plan holds no placeholders: ask for a missing fact or access in this report. Before a write to production data, save the rows it changes. Say whether the project's Gate (`## Settings` in the project rules) runs before a push; when it takes longer than the harm can wait, let the user decide. The user's go approves this plan as written.
5. **Mitigate and confirm.** Carry out the plan as approved, handing the user each step that is theirs as its exact command and waiting for their word that it is done. When anything departs from it, stop, report, and wait for go. Make code changes in a worktree off the latest default branch (`EnterWorktree`), never in the user's checkout. When the default branch takes direct pushes, push the change straight to it; otherwise open a PR through the `git-provider` skill and merge it once the branch's own rules allow. Then show the harm stopped with the plan's checks: the step 2 count before and since, over a window in which the old rate would have shown several, or the check step 3 named when the mitigation does not move that count. When it has not stopped, go back to step 3 with what you learned. When the proof can only come later (a job's next run), say when and how to check it.
6. **Hand off.** File the long-term fix through the `ticket-provider` skill: the root cause, the mitigation, what it took from users that must come back, when the mitigation can be undone, anything changed outside the repo that the repo must now match, and the timeline. Then put the damage to the user: who was harmed (the step 2 query, to rerun), what happened to them, and whether a remedy for harm already done, such as refunds, a notice, or an audit for misuse, is warranted. File the remedy they decide on as its own ticket.

**Reply:** what broke and why, who it hurt and how many, the severity, the mitigation and the proof it held, what it cost users, the tickets with the links the `ticket-provider` skill returned, and last, the remedy question.
