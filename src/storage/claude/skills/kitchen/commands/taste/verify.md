# Verify: does the change work

You did not write this change. Run it the way a user would, base against head, and give it `PASS`, `PASS+NOTES`, or `FAIL`. Only a verdict from a session or agent that did not write the code counts: an author checks what it meant to build, and you check what it built. You change no code and push nothing.

[Taste](taste.md) step 2 dispatches you before the PR, in full or targeted at what a fix changed. After the PR, when a change lands that no verdict covers, the scheduler starts you (`/kitchen taste verify <KEY>`, phase `verify`) whatever the order's mode, or, with the user here on any order but an auto one, [merge](../cook/recipes/merge.md) dispatches you as a fresh agent. Never run `kitchen.zsh order claim`: the order stays with whoever holds it.

- **Before the PR**: skip step 3, which taste step 1 ran, and steps 7 and 8, since the final review answers the review criteria and records the verdict. Reply with your findings.
- **Targeted**: the caller names the fix. In step 4 drive only the done-when lines and flows the fix could change, found per the [blast radius](../cook/stations/blast-radius.md) station, and in step 5 audit only the fix's diff.

1. **Read the order**: `kitchen.zsh order get <KEY>` (`kitchen.zsh` here and below is `~/.claude/skills/kitchen/dependencies/scripts/kitchen.zsh`; run it by that path) for the intent, the done-when, the PR, and any earlier verdict's `verdict_notes`. Read the diff, and the PR body when there is one, through the `git-provider` skill. Every claim in them is something to check, not evidence.
2. **Check out the branch head on your own.** As a scheduler session, `EnterWorktree` with `name: verify-<KEY>`; as a dispatched agent you already have a worktree. Then `git fetch origin <base> <branch>` and `git checkout --detach origin/<branch>`; before the PR, the caller names the head commit instead: `git checkout --detach <sha>`, which your worktree shares. The base branch is what `kitchen.zsh order base <KEY>` prints, with `-` for the key outside an order. On a workspace line, take this step from the type's doc (`kitchen.zsh workspace` prints its path), and read what it adds to the steps after it. There `kitchen.zsh workspace enter <KEY> verify-<KEY>` checks each repository out at the head of the order's branch and prints the worktree to work in.
3. **Re-run the gates**: `bash ~/.claude/skills/kitchen/dependencies/scripts/contract-check.sh origin/<base> --run`, which confirms nobody but the contract author touched the tests and each one ran and passed (on a manual order it prints `no contract commit`, which passes: the tests are the user's, per the [contract](../cook/stations/contract.md#a-manual-order) station, and the Gate runs them), then the `Gate` in the project rules (`.claude/kitchen/house.md`). After each step, run `kitchen.zsh order set <KEY> "step=verify <n>"` so the scheduler sees progress.
4. **Drive the change live** through the project's verify skill (`.claude/skills/verify*`), else the `run` skill: each done-when line, checked per [done-when](done-when.md), then the flow the intent names, end to end, on the head and on the base. Drive it even when no done-when line names a behavior, unless the change has no runtime surface; say which. When the verify skill fails at a step the app handles correctly, report verify-skill drift, not a finding. When a drive needs a browser and the project has no Playwright MCP config, or hits a locked profile, stop and report it. Drive at least one behavior with inputs you pick yourself, never a contract test's: the coder saw those, and code shaped to them passes them. A line that passes on both cannot see the change; say so. A change to a shared interface drives each consumer's flow too. Keep the evidence (screenshots, outputs, logs) where the verify skill says it survives cleanup.
5. **Audit the diff against the intent**, distrusting the PR body: what the intent needs that the diff lacks, and what the diff does that the intent does not need. Each suspicion becomes a run, per the [blast radius](../cook/stations/blast-radius.md) station's proof ladder. Leave mutation testing out: taste's mutation sweep already ran the contract against every changed line, and the order's `decisions` record each mutant it called equivalent.
6. **Judge.** Block only on a problem you can show with a run at the head: a bug a user would hit, a failed gate, or a doc line the PR made wrong. A problem the base already has blocks only when the PR copies it or newly reaches it. Everything else is a note.
   - `FAIL`: at least one blocking problem.
   - `PASS+NOTES`: nothing blocks, and something should still change. Each note is fixed before the merge, as a `FAIL` finding is.
   - `PASS`: nothing blocks and nothing to add.
7. **Answer the review criteria.** Read Questions that hold a PR in the project rules (`kitchen.zsh rules`) and answer each question for this change, from the diff and your runs. Keep each one that holds as a reason, `<question>: <why, with file:line>`. Answer for the change itself, never for the code around it.
8. **Record it.** Write the notes to a file: for each finding the command, the output it printed, and what the intent requires; for a pass, what you ran and saw. From the checkout of the head you verified, run `kitchen.zsh order verdict <KEY> <WORD> @<file>`, followed by each step 7 reason as its own quoted argument. Post nothing on the PR.
9. **Clean up** what you started, keeping the evidence, then `ExitWorktree` with `action: "remove"`.

**Reply:** the verdict, the review criteria that hold, what you ran on head and base, each finding with its command and output, and where the evidence is.
