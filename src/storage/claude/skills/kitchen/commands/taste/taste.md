# Taste: hold the quality gate

[Open a PR](../cook/recipes/open-a-pr.md) runs this as the quality gate on every order; `/kitchen taste` runs it on any branch.

Nothing reaches a PR until it works and reads well. The Gate runs first because it costs no tokens. Then an agent that did not write the change proves it works, two reviewers read it for quality, and one reviewer on another model reads the whole change for what the rest missed and gives the verdict. Every agent pays to load the change, so each reads it once per round, and a re-check after a fix covers only what the fix touched. Only what a run proves counts as a bug.

## Inputs

- **The branch**: the current one unless named; check a named one out here first, and when git refuses (uncommitted changes, or another worktree has it), say why and stop. The base branch is what `kitchen.zsh order base <KEY>` prints, with `-` for the key outside an order.
- **The order key**, when cook runs this; otherwise `-`. Run on its own, commit each fix on the branch and leave pushing to the user. When the order's `mode` is `manual`, the user wrote the code: follow [a manual order](#a-manual-order) below, under which the gate reports and fixes nothing.
- **The done-when**: the order's, when there is one. Otherwise derive it from the PR description and commit messages: each claim of what now works becomes a check.
- **The project rules**: what `kitchen.zsh rules` prints, which reads the base branch's copy before the working file, so a worktree without `.claude/` still has them. When it is missing, run the general reviewer alone, Reach `touched lines`, and the project's own lint, type, and test commands, and say so.
- **On a workspace line** (`kitchen.zsh workspace` prints the path of the type's doc), take step 1 and the reviewers' diff ranges from that doc. It runs the Gate once across the order's repositories, and the contract check and the mutation sweep through `kitchen.zsh each <KEY> --changed`, once in each repository with commits and against that repository's base. Steps 2 and 5 dispatch without `isolation`, since the workspace is not a git repository: each agent runs `kitchen.zsh workspace enter <KEY> verify-<KEY>` and works, and records any verdict, from the worktree it prints. A finding names its repository.

## Steps

Under an order, after each step run `kitchen.zsh order set <KEY> "step=taste <n>"` so the scheduler sees progress.

1. **Gate.** Fix until all three pass.
   - **The contract held**: `bash ~/.claude/skills/kitchen/dependencies/scripts/contract-check.sh origin/<base> --run`. A broken lock means a coder edited the contract: take that edit out of the branch, never bless it with a new contract commit. A failed or missing test goes back to the code. `no contract commit` on code a recipe shipped means its [contract](../cook/stations/contract.md) step was skipped: run it now. Run on its own, report it.
   - **The Gate passes**: run the `Gate` command from the project rules and fix until green, before the sweep: a survivor on code the Gate calls unread is a deletion, not an equivalent. Run any enforcement script the Gate does not yet include before it, until `/kitchen open` folds it in.
   - **Every changed line has a test that fails when it breaks**: with the tree clean, run `python3 ~/.claude/skills/kitchen/dependencies/scripts/mutation-sweep.py origin/<base>`, which mutates each changed source line and runs the contract against each mutant. Brief the contract author once with every survivor it lists: pin each, or name it equivalent with the reason no test can tell it apart. Record each equivalent with `kitchen.zsh decide <KEY> "equivalent mutant: <path:line> <operator>: <why>" "<the sweep's output file>"`. Rerun the sweep on the correction until every survivor is pinned or recorded. A changed file it cannot mutate prints as `not swept:` (exit 3); for each that is source, not a test or config, check every contract test that covers it by hand: break the behavior the test names (a wrong value, a skipped effect, the effect done twice), run that test, see it fail, and `git restore` the file. A test that still passes proves nothing or never ran: have the contract author fix or cut it.
2. **Verify.** Dispatch a fresh agent on the verify role with `isolation: "worktree"`, told to follow [verify](verify.md) for this order before the PR, in full, at the head commit (`git rev-parse HEAD`), which its worktree shares; nothing is pushed. It drives every done-when line and the flow the intent names, head against base, and reports findings; it fixes nothing. Fix each per [Fixing a finding](#final-review), run step 1 again, and dispatch a targeted verify: a fresh agent on the same role, told to follow verify before the PR, targeted at what the fixes changed. Repeat until a verify reports nothing; a third targeted verify with findings parks the order as step 5 does. When the drive needs a browser and the project has no Playwright MCP config, or the agent hits a locked profile, run the `playwright-mcp-setup` skill and dispatch again; headless, run `kitchen.zsh order set <KEY> status=86 "reason=parked: driving the app needs the playwright-mcp-setup skill run in this project"` and end. When it reports verify-skill drift (a step the app handles correctly that the skill fails), fix the skill's map on this branch per [calibrate](calibrate.md), never the app, and verify again.
3. **Taste**, two reviewers in parallel, each reading the diff once:
   - **General**: one `taster-agent` given every check under [General checks](#general-checks).
   - **Project**: one `taster-agent` given every convention the project rules tag `review: project`. With none tagged, the general reviewer runs alone.

   Give each the project rules' `Reach`, the diff range `origin/<base>..HEAD`, the change's intent, the project's conventions tagged with one of its checks (`review: <check>`, or `review: project` for the project reviewer), and each check's known classes from `kitchen.zsh classes <check>` (none when the project is not registered). The general reviewer also gets the contract test paths and step 1's contract check output, for its gaming check. Fix what is inside reach, then log every finding per [Logging findings](#logging-findings); the project reviewer's findings log under `project`.
4. **Gate again**: the Gate, then the mutation sweep with `--since <the head step 1 swept>`, so it mutates only what the fixes changed. When a fix in step 3 changed behavior, dispatch a targeted verify as step 2 does.
5. **Final review.** Dispatch a fresh agent on the other family role, a model other than the author's, with `isolation: "worktree"`, the head commit, and the first brief under [Final review](#final-review). It reads the whole change once, and with no findings it records the verdict. For each finding it reports, rerun its command yourself; keep it when the output shows the failure and the failure breaks the intent, and record the rest as unproven per [Final review](#final-review). When you keep none, send the re-review brief anyway, with each finding's rerun and why it does not hold. Otherwise fix what you keep, run step 4, and send the same reviewer the re-review brief and the new head commit with `SendMessage`: it still holds its first read, so it checks only the fixes, the way a person re-reviews a PR. It approves by recording the verdict, or reports what the fixes left; fix that and send it back. When the reviewer can no longer be reached (a new session), give a fresh agent on the same role the re-review brief with its findings. A third re-review with findings ends the loop: with the user here, hand the findings back; headless, run `kitchen.zsh order set <KEY> status=86 "reason=parked: three re-reviews with findings"` and end. Run on its own (the key is `-`), the reviewer reports and records nothing.
6. **Report**: each done-when line with the verify's evidence, the sweep's survivors and how each was settled, what each reviewer found and what you fixed, the final review's findings, the fixes and what each re-review found, the verdict, and what is left for the user. Run from an order, carry on at the next step of [open a PR](../cook/recipes/open-a-pr.md); run on its own, give the report to the user.

## General checks

The general reviewer's checks, each finding labeled with the one that found it.

- **tidy**: what the next person to read or change the code within reach would trip on. Unclear names, needless indirection, dead code, duplicated logic, the same switch on a value's kind repeated in several places, one logical change that must be made in many places, a bare string or number standing in for a domain value such as an ID, money, or a unit.
- **consistency**: the change does something the codebase already has a way to do, and does it differently or builds it again. The existing way wins.
- **test-honesty**: a test the change adds outside the contract, a test that would still pass if the behavior it names broke, a test that fails when only internals change, or a mock of the thing under test.
- **minimal**: code the done-when does not need. Speculative options and parameters, an abstraction with one caller, defensive handling of a state the types or callers rule out, files touched that the change did not require.
- **gaming**: code that passes the contract without doing what it promises. A branch on a test's exact inputs or on running under test, a test's expected value hardcoded in source, a change to the test runner's config, setup, or skip markers that changes what runs, and a contract commit made after the code that weakens a test.
- **comments**: a comment that restates the code, narrates the change or its history, or excuses code that should change instead. Keep a comment only for a non-obvious why the code cannot show; a comment excusing code flags that code too.

## Final review

The first brief:

> You did not write this change. Check out the head commit the caller names (`git checkout --detach <sha>`) and read all of it against its base (`git --no-pager diff origin/<base>...HEAD`), with the intent, the done-when, and the verify reports. Find what the earlier steps missed: bugs a caller would hit, what the intent needs that the change lacks, tests that pass for a reason other than their line, and docs the change made wrong. Prove each finding with a run against the real code, such as a failing test, a repro script, or command output that shows the wrong behavior, and report the command, the output it printed, and the output the intent requires. Leave out anything you did not run, including style and naming, which the reviewers covered. The mutation sweep already ran, so a mutated line the tests miss is not a finding. Then answer each question in the project rules' Questions that hold a PR section (`~/.claude/skills/kitchen/dependencies/scripts/kitchen.zsh rules`) for this change, keeping each that holds as `<question>: <why, with file:line>`. Each convention marked `my review` that the change falls under holds too, as `<convention>: <why>`. With no findings, write what you read and ran to a file and, from the head you reviewed, run `~/.claude/skills/kitchen/dependencies/scripts/kitchen.zsh order verdict <KEY> PASS @<file>`, followed by each question that holds as its own quoted argument. With findings, record nothing, and report them with the head you reviewed.

The re-review brief:

> The author answered your findings. Check out the new head commit the caller names (`git checkout --detach <sha>`; when your worktree is gone, first `git worktree add --detach <a scratch directory> <sha>` and work there) and read only the range the caller names, by default what changed since the head you reviewed (`git --no-pager diff <reviewed head>..HEAD`). Rerun each finding's command: it must now print the output the intent requires. A finding the author rejected comes with its rerun and why it does not hold; it stands only if you prove the failure again. Then look for anything the fixes broke, proven by a run as before; leave the rest of the change alone, since you already reviewed it. Re-answer a question that holds a PR only when a fix changes its answer. With nothing left, record the verdict as the first brief says, from the new head. Otherwise record nothing, and report what is left with the head you reviewed.

**Why the re-review reads only the fixes.** Reviewing the whole change again finds a little more and invents much more: in one study, multi-turn review raised false positives 62% while recall rose 0.08 (arXiv 2603.16244). The reviewer that read the change checks only what the fixes changed, and only a finding a run proves changes code.

**Fixing a finding** from the verify or the final review. Read every function on the path end to end before editing; a finding names a symptom and a line, and the defect is often neither. Fix it yourself at its root, its repro joining the contract per the [contract](../cook/stations/contract.md) station where a test is cheap, and commit the fix as a fixup of the commit that introduced the bug, and say whether it changed behavior, since that decides the targeted verify. A recurring finding lists examples only; sweep the diff for the rest. Sweep for the claim, not the symbol: everywhere that quotes the old behavior is stale, and a grep for the symbol will not find it; check the wiring module, the entry point, and the README.

A suspected bug no run could reproduce is not confirmed: record it with `kitchen.zsh decide <KEY> "unproven: <scenario>: <why no run reproduced it>" "<the command you ran>"` (in your report when the key is `-`), and change no code for it.

## Logging findings

Log each reviewer finding, inside reach or not, under the check that found it, its one-line note written to a file first:

    kitchen.zsh catch <KEY or -> <check> <class> @<file>

- `promote`, once per class however many catches print it: search the base branch for the pattern the catches describe.
  - **Found in a few places, or anywhere the fix is mechanical** (the same edit at every site, and the search that found them finds none after it): fix them all on this branch, however many, then, run from an order, `kitchen.zsh promoted <class> <KEY>`.
  - **Found in more places than this branch can fix without doubling its diff, each needing its own judgment:** the codebase taught the slip, so it gets a cleanup, not a check. Search the tracker per [left for you](../cook/stations/left-for-you.md#discovered-issues) for an open ticket cleaning it up; one found answers it: `kitchen.zsh promoted <class> <its key>`. Otherwise it is one candidate for the class: with the user here, ask it in the same hand-back question as the real slips below; headless, the escalation agent decides it per [left for you](../cook/stations/left-for-you.md#triage). A ticket filed for it is "Clean up <class>": how many instances and where, the command that finds them, and what to write instead per the language's, stack's, and industry's best practice, with sources. Open no order for it: it enters the line when the user takes it. Then `kitchen.zsh promoted <class> <its key>`, or `-` when it is left.
  - **Not found:** a real slip, and only the user decides on a check. Search the tracker the same way for an open "Enforce <class>" ticket; one found answers it: `kitchen.zsh promoted <class> <its key>`. Otherwise file nothing. With the user here, ask once at the hand-back about every due class together, each with its catches: one "Enforce" ticket for them all, or leave them. On their go, file it listing each class's catches, open no order for it (it enters the line when the user takes it), and run `kitchen.zsh promoted <class> <NEW-KEY>` for each class; for each class they leave, `kitchen.zsh promoted <class> -`, which drops it from the catch-up until its next catch makes it due again. Headless, file nothing: the class stays due until a session with the user asks it.
- `climb <ticket>`: the slip came back after `<ticket>` landed. Handle it as a real slip; a check it asks for starts at least one rung above any `<ticket>` built.
- `kitchen.zsh catch` fails when the project is not registered: then skip logging and list the findings in your report.


## A manual order

The user wrote the code, so the gate reports and fixes nothing. Run every step above except the fixes, and:

- **Step 1**: the tests are the user's, with no contract commit ([contract](../cook/stations/contract.md#a-manual-order)), so `contract-check.sh` exiting 2 (`no contract commit`) passes. Run the mutation sweep with `--test-cmd "<the command that runs the test files the branch adds or changes>"`, and when it adds or changes none, that is the finding. Each survivor, and each hand-checked test that still passes, is a finding, not a brief to the contract author.
- **Step 2**: one verify, and its findings join the report.
- **Step 3**: the test-honesty check does not flag a test for being outside the contract, and the gaming check gets the test files the branch adds or changes as the contract paths. Log each finding per [Logging findings](#logging-findings), and fix none.
- **Step 5**: one full review. It records `PASS` only when it finds nothing; otherwise its findings join the report.
- **The report**: every finding, worst first, each with its evidence (the command, its output, the file and line). Say that nothing is fixed.

The user fixes and says "done" again. Rerun the steps their fixes could change, with a targeted verify in place of a full one and the reviewer's re-review in place of a new review, and report only what is still open.
