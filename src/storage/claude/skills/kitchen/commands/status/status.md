# Status

The user wants to know what the pipeline did and what waits on them. Catch them up in the shape of the [ketchup](../cook/stations/ketchup.md) station: what waits on them first, then what happened, then every call they own with what they need to make it from your reply alone.

1. **Gather.** Run `kitchen.zsh status` once, in the project; it marks everything it shows as seen for this project only, so a second run shows nothing new. Outside a registered project it exits 1: say so, offer `/kitchen open`, and stop. It lists the `PROMOTE`, `BLOCKED`, and `REVIEW` rows that wait on the user, then the `READY` rows (deployments at their skeleton, then manual orders, then guided) waiting for them to start, then what happened since the user last looked here (merged, with the calls made alone listed under each merge that never waited for review; dropped; filed follow-up tickets; promoted; notices), then the `now` line. For each `REVIEW` row, read the order (`kitchen.zsh order get <KEY>`) and the PR's live state through the `git-provider` skill, not the order's last word on it. A row whose PR the live check shows merged gets `kitchen.zsh order close <KEY>`, so an order closes when the user merged it even with the scheduler off.
2. **Write the catch-up** per the ketchup station, with what `kitchen.zsh status` marked new as the point to catch up from. Each merged, dropped, filed, or promoted line becomes one plain sentence on what changed for the user; a call made alone under a merge keeps its evidence. Act on a notice only when the user asks.
3. **The calls**, one bullet each, riskiest first, with the ticket or PR link, what it changes for users, the evidence behind your pick, its risk, and your pick:
   - `BLOCKED`: a ready order that waits on a dropped one and starts only once the user brings that one back (`kitchen.zsh signoff <KEY> @<file>`) or takes it out of the waiting order's `after` (`kitchen.zsh order set <KEY> after=@<file>`).
   - `PROMOTE`: a kind of slip the gate keeps catching that nothing checks yet, with its catches indented under it. They are asked together, as one call, per [taste](../taste/taste.md) step 6's real-slip case.
   - `REVIEW`: the PR and why it waits (in parentheses on the row), and its verdict, a `FAIL`'s findings included (`verdict_notes`). The user reads the PR in the browser and approves it the way the `git-provider` skill's Approve PR operation says for its host, and it merges; a manual order's PR is the exception: the kitchen never merges it, and the user does. To change a PR they ask for its session, which `kitchen review <KEY>` on the row opens; an `auto` order becomes `guided`, and a manual one stays manual. A row carrying `kitchen stage <KEY>` is a catering deployment, read staged instead: that command opens its whole change staged in a new VS Code window, and the user is its last check. A `[catering]` row is a catering order's docs PR from its wrap-up.
   - `READY`: not a call; an order waiting for the user to start it. Say how many wait per mode, and that `/kitchen next manual`, `/kitchen next guided`, or `take <KEY>` starts one. A `skeleton` row is a deployment whose skeleton is built with the user, whatever its mode: offer `take <KEY>`. A `[catering]` row is planned or wrapped up with the user, never by the scheduler: offer `/kitchen cook <KEY>`.
4. **Act on the user's answers**, in their words:
   - Promotions: per taste step 6's real-slip case, from the project's folder.
   - Drop an order: write their reason to a file, run `kitchen.zsh order set <KEY> status=86 reason=@<file>`, and comment the reason on the ticket.
   - Bring a dropped one back (`kitchen.zsh order list 86` lists them): `kitchen.zsh signoff <KEY> @<file>` with their words; for a `[catering]` one, `kitchen.zsh order set <KEY> status=ready`, then offer `/kitchen cook <KEY>`. A parked one (its reason starts `parked:`) comes back once what parked it is fixed, as `guided` (`manual` when guided is locked): `kitchen.zsh order set <KEY> mode=guided`, then `kitchen.zsh signoff <KEY> @<file>`.
5. **When nothing happened and nothing waits**, say so in one line.
