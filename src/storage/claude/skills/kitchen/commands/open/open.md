# Open a project

Set the current project up for the pipeline, with the user: its project rules (what gets checked on every change, and what enforces each rule), its verify skill (how an agent drives the app the way a user does), and its registration with the pipeline. The project rules and verify skill are committed to the project and are the user's to edit. Every step is idempotent: re-running `open` repairs what is missing and leaves the rest.

1. **Equipment.** `ticket.zsh provider` (from the `ticket-provider` skill) must print the project's tracker; if it fails, run that skill's setup first. Run the `git-provider` skill's pre-flight for the project's host, and confirm `kitchen.zsh order base -` prints the branch work merges into.
2. **Project rules.** Write `.claude/kitchen/house.md` from [templates/house.md](templates/house.md), or refresh the one that exists.
   1. **Find the mistake classes** per the [correct](../cook/stations/correct.md) station: what the project already enforces (its lint, type, formatter, and CI config, the conventions in its `CLAUDE.md`), the review comments on the last 20 merged PRs (through the `git-provider` skill), and the last 50 commits for reverts and fix-ups. A class seen twice is a rule.
   2. **Give every rule its enforcer**, at the highest rung that works, per the correct station: structure, then types, then a lint whose error names the fix, then a test, and only last a taster that reads for it. A rule nothing enforces does not go in. A rule whose enforcer does not exist yet goes in with the taster that reads for it today. When the code already breaks it in more places than a small PR fixes, file its cleanup ticket per [taste](../taste/taste.md) step 6 instead of building a check. Otherwise propose its check to the user, with how it would work and your recommendation, and build the ones they agree to in this session per the [enforce](../cook/recipes/enforce.md) recipe's steps 2 to 5, showing them each proof.
   3. **Settings.** `Gate`: the one command that runs the tests, lint, and build; run it once to confirm it works on the base branch. `Reach`: how far tasters may tidy, asked of the user. `## Critical`: paths where a mistake loses money, data, or a safety check, asked of the user. `## Always review`: the paths whose changes always wait for the user; show the template's defaults and ask which to keep and what to add. `## Review when`: the questions a verifier answers to decide whether a change waits for the user, asked of the user.
   4. **Show the draft**, with every template placeholder the user did not fill deleted: the `<rule>` row and the example lines under `## Critical`, `## Always review`, `## Review when`, and `## Sorting`. Both review sections stay, empty or not. The user edits it; their word wins.
3. **The verify skill.** If neither `.claude/skills/verify/` nor a `.claude/skills/verify-<app>/` exists, generate it per the [create a verification skill](../cook/stations/create-verification-skill.md) station, proving it end to end before handing it over. If it exists, bring its Launch up to that station's rule that each instance gets a port and data directory of its own, so two worktrees can each run one.
4. **The ready section.** The scheduler takes tickets from `ticket.zsh ready`, the queue the project's ticket-provider config names. Show the user the first five it would take (`ticket.zsh ready 5`, then `ticket.zsh get` for each title), and when it is not the part of the board they mean, change the config's `ready` per the provider's mode and show them again.
5. **Register the project**: run `kitchen.zsh line add .`, which prints the project's slug; running it again changes nothing. When the verify skill's Launch cannot give each worktree its own port and data directory, the app cannot run twice at once: `kitchen.zsh line set <slug> max_cooking=1`.
6. **Tell the user** in four lines: the project rules and verify skill are written and theirs to commit, and the project counts as set up once its base branch holds them (`kitchen.zsh house` says `set up`); the project is registered; its first five PRs wait for their review; and if the scheduler is not running yet, it starts by setting `enabled = true` in this skill's `automation.toml` in ohMyZshConfig and running `make deploy-automations`.
