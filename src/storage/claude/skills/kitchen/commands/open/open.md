# Open a project

Set the current project up for the pipeline, with the user: its project rules (what gets checked on every change, and what enforces each rule), its verify skill (how an agent drives the app the way a user does), and its registration with the pipeline. The project rules and verify skill are committed to the project and are the user's to edit. Every step is idempotent: re-running `open` repairs what is missing and leaves the rest.

A directory of several git repositories, not one, registers under a workspace type, one of the directories under `~/.claude/skills/kitchen/workspaces/`. Before step 1, read that type's doc, `<type>/<type>.md` there, and take its version of each step below that it names. Its version of step 4 registers the line with `kitchen.zsh line add <path> --workspace <type>`.

1. **Equipment.** `ticket.zsh provider` (from the `ticket-provider` skill) must print the project's tracker; if it fails, run that skill's setup first. Run the `git-provider` skill's pre-flight for the project's host, and confirm `kitchen.zsh order base -` prints the branch work merges into.
2. **Project rules.** Write `.claude/kitchen/house.md` from [templates/house.md](templates/house.md), or refresh the one that exists.
   1. **Find the conventions**: what the project already follows and enforces (its lint, type, formatter, and CI config, any conventions file and its check, the conventions in its `CLAUDE.md`, and any reviewer agent it defines), the industry practices that apply to it (an accessibility standard, a privacy rule, the language's formatter), and its mistake classes per the [correct](../cook/stations/correct.md) station: the review comments on the last 20 merged PRs (through the `git-provider` skill) and the last 50 commits for reverts and fix-ups. A class seen twice is a convention.
   2. **Give every convention its enforcer**, at the highest rung that works, per the correct station: structure, then types, then a lint whose error names the fix, then a test, and only last a reviewer that reads for it: `review: <check>` when one of taste's [general checks](../taste/taste.md#general-checks) covers it, else `review: project`, or `my review` when only the user can judge it, since the final review then holds its PR for them. Write each convention as one line under its topic, ending with its enforcers, and list each script it names under Enforcement scripts by that name. When the code already breaks a convention in more places than a small PR fixes, file its cleanup ticket per [taste](../taste/taste.md#logging-findings) instead of building a check. Otherwise propose its check to the user, with how it would work and your recommendation, and build the ones they agree to in this session per the [enforce](../cook/recipes/enforce.md) recipe's steps 2 to 5, showing them each proof.
   3. **Fill Kitchen setup** with the user.
      - `Gate`: one command that runs this project's checks in order, fastest first, and stops at the first failure. Decide its steps with the user: each enforcement script, and whichever of the project's linters, formatters, type checkers, tests, and build they want; a project may have only linters. Use the project's own committed command when one does this (a make target, a package script). Otherwise write the steps as a script in this project's order book directory (`~/.claude-artifacts/workflows/kitchen/<slug>/gate.sh`), outside the repo so nothing is committed, and record the command that runs it. Time each step once on the base branch to set the order, and confirm the whole command passes there. `Mutation`, skipped when the line is already set: when the project has JavaScript or TypeScript source, propose Stryker so taste's mutation sweep covers it. On the user's go, install `@stryker-mutator/core@10.1.1` as a dev dependency with the project's own package manager, and commit the manifest and lockfile change to the base branch, since worktrees start from it. Record `stryker` and the command that runs it in backticks (such as `npx stryker run`), then prove it: on a scratch branch with one commit that adds a known test gap to a small file, `python3 ~/.claude/skills/kitchen/dependencies/scripts/mutation-sweep.py <base> --test-cmd "<that file's test command>"` must list the gap as a survivor and leave `git status` as it was. Record `off:` and why instead when the user declines or it cannot be made to work; a project with no JavaScript or TypeScript drops the line. `Reach`: how far reviewers may tidy, asked of the user.
      - **Critical paths**: one line on what makes a path critical in this project, then one row per path, its extended regular expression in backticks with each `|` written `\|` so the table holds. Show the template's rows and ask which to keep, then ask what else would lose money or data, expose it, or weaken a check that guards it (Extra effort), and what else always waits for them (Waits for me).
      - **Questions that hold a PR**: the questions the final review answers for every change, one `- <question>` each, asked of the user.
      - **Intake defaults**: starts empty; intake proposes a line when the user overrides it the same way twice ([mode](../serve/mode.md)).
      - **Docs**: `- <what>: <where>`, found from the project's docs directories and README and confirmed with the user; `- none` when it keeps none.
      - **Production**: asked of the user; leave out what they do not know.
   4. **Show the draft**, with every template placeholder the user did not fill deleted. Critical paths, Questions that hold a PR, and Docs stay even when empty, since `kitchen.zsh house` treats a project missing one as not set up, and it names any path row it cannot read. The user edits it; their word wins.
3. **The verify skill.** If neither `.claude/skills/verify/` nor a `.claude/skills/verify-<app>/` exists, generate it per the [create a verification skill](../cook/stations/create-verification-skill.md) station, proving it end to end before handing it over. If it exists, bring its Launch up to that station's rule that each instance gets a port and data directory of its own, so two worktrees can each run one.
4. **Register the project**: run `kitchen.zsh line add .`, which prints the project's slug; running it again changes nothing. When the verify skill's Launch cannot give each worktree its own port and data directory, the app cannot run twice at once: `kitchen.zsh line set <slug> max_cooking=1`.
5. **Tell the user** in four lines: the project rules and verify skill are written and theirs to commit or not, and the project counts as set up once the rules exist (`kitchen.zsh house` says `set up`); a copy committed on the base branch wins over the working file; the project is registered; the project starts manual-only, co-write unlocks after 2 merged manual orders, guided after 3 merged co-write ones, and auto after 5 merged guided ones (`kitchen.zsh line set <slug> <mode>_after=<n>` lowers a threshold); and if the scheduler is not running yet, it starts by setting `enabled = true` in this skill's `automation.toml` in ohMyZshConfig and running `make deploy-automations`.
