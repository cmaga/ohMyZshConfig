# Follow a PR

Drive an open PR to merge-ready: conflicts, review threads, a failed verdict, and checks. The scheduler runs it when a PR changes; the user runs it with "check on PR X", "get it green", or "address the comments".

**You own the PR's frontier. Declare a mode, clear one thing at a time, stop where the user's call begins.**

1. **Declare the mode before anything else.** `drive` runs to merge-ready and is the default, and what the scheduler's wake means. `threads-only` answers review comments and touches nothing else ("address the comments"). `check` is one status pass and a report ("check on X", "is it green"); a small or docs-only PR the user asks about gets `check`.
2. **Claim the order**: `kitchen.zsh order claim <KEY>`. `order pr` and `order verify` handed it to the scheduler, so take it back before acting. A refused claim means another session holds it: say so and stop. Read the PR's state through the `git-provider` skill:
   - **Merged**: `kitchen.zsh order close <KEY>`, and end.
   - **Closed without merging**: as [cook](../cook.md) step 7 says.
3. **Work in this order: conflicts, then review threads, then the verdict, then checks.** Batch every known fix into one push: fixups, folded and pushed per [open a PR](open-a-pr.md) step 4. A conflict you resolve on the order's own branch; touch no other branch.
4. **Comments.** Act only on PR comments whose id is not in the order's `handled`. Right after each reply you post and each comment you act on, run `kitchen.zsh order set <KEY> handled=@<file>`, the file holding a JSON array of the old `handled` plus those ids, since a session can die between any two steps. Start every PR comment you post with `kitchen:`; a comment that starts with it is your own, so add its id to `handled` and act on nothing in it. Post replies with the body in a file (`gh api --method POST repos/<owner>/<repo>/pulls/<pr>/comments/<id>/replies --input <payload.json>` on GitHub); never put comment text on a command line.
   - **The user approved**, by an approving review or a comment from the user that reads `approve`: `kitchen.zsh order approve <KEY> <the PR head commit when they approved>`.
   - **An answer to a Left for you item**: act on it (file the ticket, fold the fix, or drop it), record it with `kitchen.zsh decide`, the comment's link as the evidence, and log no catch.
   - **Any other comment from the user** is a fix and a catch. Fix it, write the lesson to a file, run `kitchen.zsh catch <KEY> chef <class> @<file> --chef`, and handle `promote` as [taste](../../taste/taste.md) step 6 does. A comment that asks something only the user can answer is a call only the user can make.
5. **Comments from anyone else, review bots included**: skeptical posture. Bots catch real bugs and also file non-issues and nitpicks, so check each claim against the code. Fix a real one with a failing run first: where a test is cheap, its repro joins the contract per the [contract](../stations/contract.md) station before the fix; dismiss noise on its thread with the concrete disproof; escalate anything touching security, auth, billing, data, or migrations rather than dismissing it yourself. Never churn code to quiet a bot.
6. **A `FAIL` verdict** (`kitchen.zsh sample` prints `fix`): each finding in the order's `verdict_notes` is a claim from a session that ran the change. Reproduce it, add the reproduction to the contract per the [contract](../stations/contract.md) station where a test is cheap, and fix it at its root. A finding you cannot reproduce gets a `kitchen.zsh decide` row with the command you ran; the next verdict settles it.
7. **Classify a red check before any rerun.** A failure in code the diff never touched, when `git merge-base --is-ancestor origin/<base> HEAD` fails, is a stale base: repeat open a PR step 4. A flake or infrastructure failure earns one rerun (`gh run rerun <run-id> --failed` on GitHub), never more: an identical second failure was never flake, so read the logs. Only a failure in the diff's own code gets a commit, a fixup.
8. **Stop at the user's line.** The user's review is a wait, not a blocker to fix. Merging happens only through the [merge](merge.md) recipe, when `sample` says `no`. In `check` mode, report the PR's state and stop. Otherwise run the [merge](merge.md) recipe.

**Reply:** the mode, what you fixed and answered, each dismissal with its reason, the verdict's state, the checks' state, and what waits on the user.
