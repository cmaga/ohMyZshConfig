# Merge

Land a PR once a verdict from a session that did not write it covers the change, and its checks pass on the base it lands on. Green is not safe: green CI and an approving bot review are not verdicts, because neither runs the change as a user would.

**You own what lands.**

1. **Ask what the PR needs**: `kitchen.zsh sample <KEY>` from the order's worktree, again before every merge. It prints one word:
   - `rebase`: the base moved under a file this branch changes, or under its checks. On a manual order a conflict is the user's, per [SKILL.md](../../../SKILL.md#autonomy). Repeat [open a PR](open-a-pr.md) step 4, then ask again.
   - `regate`: the change differs from what the quality gate passed. Run the [mutation sweep](../../taste/taste.md) (taste step 2, run as [a manual order](../../taste/taste.md#a-manual-order) says on one) and the [bug review](../../taste/taste.md#bug-review) on `git range-diff <gated_base>..<gated_head> origin/<base>..HEAD`, with `gated_base` and `gated_head` from the order; fold its fixes and push per open a PR step 4; run `kitchen.zsh order gated <KEY>`; ask again.
   - `fix`: the verdict on this change is `FAIL`. On a manual order the findings are the user's, never yours to fix: run `kitchen.zsh order pr <KEY> <url>` and end; the catch-up reports them. Otherwise fix each finding in the order's `verdict_notes` per [follow a PR](follow-a-pr.md) step 6, then ask again. A third `FAIL` (the order's `verify_fails`) parks the order: comment the findings on the PR, run `kitchen.zsh order set <KEY> status=86 "reason=parked: three FAIL verdicts"`, and end.
   - `verify`: no verdict covers this change. A verdict covers a patch, not its commits, so a rebase that changes no line keeps it. Headless, run `kitchen.zsh order verify <KEY>` and end: the scheduler starts a session that did not write the change, and wakes one here once the verdict lands. With the user here on a guided or manual order, dispatch a fresh agent on the verify role with `isolation: "worktree"`, told to follow [verify](../../taste/verify.md) for this order, then ask again. On a manual order the scheduler's follow-up stays a backup.
   - `review`: the PR waits for the user, and the order's `review_why` says why. `sample` sets it for a deleted test, an added line that silences a check, a changed check path, a `## Review when` reason in the verdict, an `## Always review` path outside the order's `station`, and always for a manual order, whose PR the kitchen never merges: the user does. The order's own `review` flag, set at intake, holds it too. Wait on the checks and fix red per step 2 without merging. Then `kitchen.zsh order pr <KEY> <url>` hands the PR to the scheduler, which wakes a session when the user acts. A comment can land while you hand it over, so list the PR's comments once more: any whose id is not in the order's `handled` means `kitchen.zsh order set <KEY> pr_seen=` and [follow a PR](follow-a-pr.md). Otherwise, with the user here, carry on from [the user's review](#the-users-review) step 2.
   - `no`: go on.
2. **Wait on the required checks** through the `git-provider` skill (its Checks operation). Where the provider has no rerun, any failure is real.
   - **Red**: on a manual order it is the user's, per [SKILL.md](../../../SKILL.md#autonomy). Otherwise classify it per [follow a PR](follow-a-pr.md) step 7 before fixing, then ask again per step 1. After three real red rounds, park the order: comment what failed on the PR, run `kitchen.zsh order set <KEY> status=86 "reason=parked: three red check rounds"`, and end.
   - **Green**: list the PR's comments; any whose id is not in `handled` takes you to [follow a PR](follow-a-pr.md).
3. **Merge** through the `git-provider` skill, after one more `sample` that prints `no`. Read the PR back for the result: a merge queue that only queued it, or a requested auto-merge, is not a merge. A landed PR reads merged, with the base as its target. Where the provider's merge only queues it (CRUX auto-merge, which lands once the required reviewers approve), run `kitchen.zsh order pr <KEY> <url>` and end: the scheduler sees it merge and a follow-a-pr pass closes the order.
4. **Close the order**: `kitchen.zsh order close <KEY>`. With the user here, end with an [exit report](../templates/exit-report.md).

A PR stacked on another merges only after its parent merged and it was moved onto the base and pushed through the `git-provider` skill; its verdict stands when `sample` says so. Leave every other branch alone while a PR lands. If a merge stalls, find out why before you change anything.

**Reply:** what landed, the verdict that covered it and who gave it, how you confirmed the merge, and anything left for the user.

## The user's review

The user reads a PR that waits on them in the browser. To change it, they ask for the order's own session: `kitchen review <ticket number>` in a terminal resumes the session that built it, from any folder, and an `auto` order becomes `guided` and a manual one stays manual. A message in a session that ran headless, other than the scheduler's `/goal Run /kitchen ...` line, is the user, and starts here.

A catering deployment is too large to read in the browser, so the user reads it staged: `kitchen.zsh stage <KEY>` checks the PR's head out into its own review worktree with the whole change staged against the base, and opens that in a new VS Code window. The `REVIEW` row in status prints the command, and step 2 runs it.

1. **Claim the order** with `kitchen.zsh order claim <KEY>` before anything else, so the scheduler starts no other session on it; a refused claim means a session is still working it: say so and stop. Work in the order's worktree: a resumed session starts in the project folder, so `EnterWorktree` with path `.claude/worktrees/<KEY>`.
2. **Answer their message, then show what still waits on them**: the PR link, why it waits (`review_why`), and the verdict. Then the order's `attention` flags and the calls in `decisions` made without them. For a catering deployment, run `kitchen.zsh stage <KEY>` first, and again whenever a change comes back with its verdict.
3. **A change they ask for** is a fix and a catch, as [follow a PR](follow-a-pr.md) step 4 treats a comment from the user; on a manual order it is the user's own to make, per [SKILL.md](../../../SKILL.md#autonomy). Push it per [open a PR](open-a-pr.md) step 4, rewrite any part of the PR description it made wrong, then run this recipe from step 1, which gets the new change its verdict before it comes back to them.
4. **When they approve** a PR that is not manual, run `kitchen.zsh order approve <KEY> <PR head commit>`, then this recipe from step 1. A manual PR they merge themselves. Once a catering deployment merges, go on per [deployment](catering/deployment.md#after-the-merge).
5. **When they leave it open**, `kitchen.zsh order pr <KEY> <url>` hands it back to the scheduler.
