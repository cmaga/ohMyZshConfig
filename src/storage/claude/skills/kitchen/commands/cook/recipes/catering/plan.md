# Plan

Turns a merged spec into milestone orders, with the user. This is the last of serving: every call the user owns is made here, and once the orders exist nothing waits on them but the PRs they flag for review. Work in the order's worktree, and keep every file this writes under `.claude-artifacts/workflows/kitchen/`, after `F="$(git rev-parse --git-common-dir)/info/exclude"; grep -qxF '.claude-artifacts/' "$F" || echo '.claude-artifacts/' >> "$F"`.

1. **Gather.** For each part (each `data-part` article) in the spec, dispatch an `Explore` agent in the background, told not to edit files, to map it onto today's code: what moves, what adapts, what is new and the spec sentence that forces it, every check today's code performs there, and what it deletes or rewrites. When the work deletes or rewrites files, one more agent per 15 leaving files lists each behavior in them, claimed by a part or `unclaimed`: the behavior no part reaches, which a reading of the spec alone never finds. Settle what the code or the spec answers yourself, recorded as a numbered line under `## Decisions` in the plan; put the rest to the user now.
2. **Plan the milestones** into `<EPIC>-milestones.md` from the [milestone plan template](../../templates/milestone-plan-template.md).
   - **M-1 is the thinnest path through the new system that runs end to end.** For a restructure, the new shape serves one real path while the old system still works.
   - Each later milestone adds one capability across the parts it touches, and ends runnable.
   - Each milestone names its **proof**: one check that fails before it and passes after, held to the verify skill's proof standards. The harness a proof needs is built in the first milestone that needs it.
   - A milestone is one PR a reviewer can read, and cheap enough to throw away whole, M-1 most of all.
   - **Move before writing.** Each milestone says what it moves, adapts, or writes new, from the gather; new code only where a spec sentence forces it, quoted.
   - Every check today's code performs, and every behavior the sweep found, lands in a milestone: moved, adapted, or retired with its reason. An `unclaimed` behavior is retired only by a spec sentence or the user's word.
   - Every part's `Owns` and every scenario in its tests lands in exactly one milestone, whose `Touches` line names the parts by the spec's ids.
   - A milestone owing one item per entry of a list longer than about 30 (a test per catalogue row, a move per file) is split.
   - `After` names the milestones it builds on. Milestones with no `After` path between them own disjoint `Files`.
3. **Approve.** Dispatch a `general-purpose` agent on the judgment role with the spec, the gather's results, and the plan. Ask for: a part's `Owns` or test scenario no milestone reaches, a `Touches` line that misses a part its milestone changes, an M-1 that does not run end to end, two milestones with no `After` path between them sharing a file, new code where a move exists, a check or swept behavior with no fate, a proof that runs on test-only settings or doubles the system's own logic, and a milestone owing more than about 30 items. Fix what it finds.
4. **Show the user the plan.** Write the page's narrative to `plan-view.json`, whose fields are listed at the top of [`plan-view.py`](../../scripts/plan-view.py), run `python3 ~/.claude/skills/kitchen/commands/cook/scripts/plan-view.py <plan> <narrative> <spec> <scratchpad>/<EPIC>-plan.html`, and publish the output with the Artifact tool. The markdown plan is for agents; the page is how the user reads it, and it is generated, never edited. Recommend which milestone PRs wait for their review: M-1 always, then any where a wrong turn would cost the most to unwind, each with one line on why. Write their picks as `**Review:** yes` and their corrections into the plan, render the page again, and go on only on their go: the orders run without them from here.
5. **Cut the spec branch** `spec/<EPIC>` from `<base>` through the `git-provider` skill (its Cut a branch operation), where `<base>` is what `kitchen.zsh order base <KEY>` prints.
6. **File and write the orders**, M-1 first, with the line paused (`kitchen.zsh line pause <slug>`, the slug `kitchen.zsh line list` shows for this project) so intake never takes a milestone's ticket before its order exists; `kitchen.zsh line resume <slug>` once the last order is written. For each milestone:
   1. A ticket under the epic through the `ticket-provider` skill: its summary the milestone's title, its description the milestone's section, linked "is blocked by" each milestone on its `After` line.
   2. Its fields, each text field written to a file first: `intent` (what becomes runnable, and for whom), `done_when` (the proof, then each test scenario of its parts that lands in it), `station` (its `Files`), `after` (the keys of its `After` milestones), and `summary` (what the gather found for its parts).
   3. `kitchen.zsh order new <MILESTONE-KEY> status=ready recipe=<its Recipe> base=spec/<EPIC> spec=<the spec's path> "parts=<its Touches ids>" review=<true when its Review is yes> intent=@<file> done_when=@<file> station=@<file> after=@<file> summary=@<file>`
7. **Hand this order to its close:** write every milestone's key to a file as a JSON array, run `kitchen.zsh order set <KEY> status=ready stage=close step= after=@<file>`. The scheduler cooks the close once every milestone is done. Headless, end. With the user here (`phase` is `session`), run `kitchen.zsh order set <KEY> pid=0`, claim M-1 with `kitchen.zsh order claim <M-1 KEY>`, enter its worktree per [cook](../../cook.md#before-starting) steps 5 and 6 (its base is `spec/<EPIC>`), end the message with M-1's goal line on the pattern of [cook](../../cook.md#the-goal-line), and end your turn. M-1 always waits for review (step 4), so its PR is the first pause.
